# Итоги: ScyllaDB, Cassandra, PostgreSQL, Redis, MongoDB, Tarantool (vinyl), RabbitMQ, RocketMQ, Kafka

Прогоны 2026-10-30 (Scylla, Cassandra, PG, Redis) и 2026-10-31 (MongoDB, Tarantool, RabbitMQ, RocketMQ). Каждый вариант прогнан один раз, 5 минут измерений. Сырые данные: `REPORT.md`, `<run>.json`, `<run>.stats.csv`.

**Условия.**
- Одна нода каждой БД, 4 CPU.
- RAM 1.5 GB вместе с page cache у Scylla, Cassandra, PG, MongoDB, Tarantool и RocketMQ.
- Redis — 6 GB (maxmemory 5 GB).
- RabbitMQ — 4 GB, порог памяти 3 GB. Почему не 1.5 GB — см. ниже.
- Стационар: 5k задач/с, очередь ~10.2M задач, `SPEED=30`, окно 08–22, payload 300 Б случайный. Исключение — строки Scylla и Cassandra с пометкой «сжимаемый».

**CPU и RAM** — среднее и максимум только за 5 минут измерений, без prefill. Поэтому цифры ниже, чем в `REPORT.md`/`docker.json`, где усреднено по всему прогону.

**Docker Desktop на macOS:** fsync медленный, абсолютные цифры занижены, смотреть на соотношения.

**Как каждая система хранит бакет.**

| Система | Хранение бакета | Запись | Чтение | Удаление прочитанного |
|---|---|---|---|---|
| Scylla, Cassandra | партиция `(hour, minute, shard)` | | | TTL или partition delete |
| PostgreSQL | часовая RANGE-партиция, индекс `(minute, shard, id)` | | keyset | DROP партиции или DELETE…SKIP LOCKED |
| Redis | LIST на бакет | | LPOP count | |
| MongoDB | коллекция на час + индекс `(m, s, _id)`, либо одна коллекция | | keyset | drop коллекции, либо deleteMany по бакету |
| Tarantool vinyl | спейс на час с PK `(hour, minute, shard, id)`, либо один спейс | | keyset | drop спейса, либо `take` (чтение и удаление страницы в одной транзакции) |

| RocketMQ 5.3 | таймер-сообщения (`TIMER_DELIVER_MS`, точность 1 с): бакетов нет, брокер сам кладёт сообщение в топик в момент исполнения | | push consumer | |
| Kafka 3.9 (KRaft) | кольцо топиков-слотов `ring-NNN` по 1 ч (26 топиков) или 5 мин (290 топиков), по 4 партиции; кольцо длиннее горизонта на 2 слота | produce acks=all в топик слота времени исполнения | закончившийся слот читается целиком до high watermark | DeleteRecords до high watermark (сдвиг log start offset = прогресс консюмера) |

**Пояснения к цифрам:**
- Scylla гонялась с повторяющимся payload: LZ4 сжимает его почти в ноль, поэтому диск занижен. Cassandra со случайным payload даёт ~325 Б на задачу; у Scylla было бы примерно так же.
- **RabbitMQ с 1.5 GB (порог 1 GB) не держит суточную очередь.** На ~5M сообщений включается memory alarm, брокер блокирует публикацию, prefill падает с 47k/s до 3–4k/s. Перерасход памяти даёт состояние каналов с неподтверждёнными публикациями (~260 MB) и процессы очередей (~220 MB). Прогон остановлен, лог лежит в `aborted-rabbit-1536m/`. Все цифры RabbitMQ выше — с 4 GB.
- **У RabbitMQ чтение страницы 374 ms (p99)** — это цена «очередь на бакет». На каждый бакет нужен отдельный канал, passive declare, consume, ack и удаление очереди. Плюс ~3600 Erlang-процессов очередей.

## Выводы

1. **Чтение по минутным бакетам дешёвое везде, кроме построчного удаления.**
   - Стационарные 8.6k/s — это 14–16 запросов/с.
   - Ломаются только варианты, где прочитанное удаляется построчно в B-tree-хранилище: DELETE…SKIP LOCKED в PostgreSQL и deleteMany в одной коллекции MongoDB.
   - LSM-движки (Tarantool vinyl `take`, partition delete в Scylla/Cassandra) удаление переносят нормально.
   - Где можно, прочитанное удаляется целиком: DROP часовой партиции, коллекции или спейса.
2. **Новые лидеры стационара — Tarantool vinyl и MongoDB с коллекцией на час.**
   - Tarantool: p99 записи 2.1 ms, 0.25–0.5 ядра, меньше всех RAM (0.57 GB из 1.5), одиночная запись до ~122k/s, батчевая ~170k/s.
   - Минус Tarantool: drain 200–250k/s — в 4–5 раз медленнее PG, Scylla и Cassandra. Чтение идёт через Lua-процедуру, это один TX-поток. Для 8.6k/s хватает с огромным запасом.
   - MongoDB с коллекцией на час: p99 2.1 ms, но 1 ядро на 5k/s по одной задаче и упор в 39k/s.
3. **PostgreSQL** — самый экономный по CPU на диске (0.27 ядра), но только с батчевой записью и DROP партиций. С одиночными коммитами при 64 соединениях не держит даже 5k/s: упор в латентность коммита. С 256 соединениями тянет 59k/s, см. раздел про пики.
4. **Брокеры под эту задачу проигрывают специализированным хранилищам.**
   - **RocketMQ** — единственный, где отложенная доставка «из коробки», без бакетов и консюмера-планировщика. Цена:
     - каждое сообщение пишется дважды (в таймер и в топик) плюс timerlog, ~1 КБ диска на задачу;
     - 1.4 ядра на 5k/s;
     - потолок 64–69k/s;
     - точность доставки ~1 с — для окна в час это неважно.
   - **RabbitMQ** — самый дорогой вариант:
     - очередь на бакет — тысячи Erlang-процессов;
     - чтение 374 ms на страницу;
     - потолок записи 22k/s;
     - для суточной глубины нужно ≥4 GB RAM — с 1.5 GB он блокирует публикацию;
     - стандартный delayed-message-exchange плагин хранит отложенные сообщения в Mnesia/Khepri в памяти и на миллионы сообщений не рассчитан.
5. **Scylla и Cassandra** — без изменений: стабильные 5–7 ms p99, большой запас по записи. Cassandra съедает весь лимит RAM и в ~2 раза больше CPU, чем Scylla. Scylla на 1 GB / 4 шарда проседает на пределе.
6. **Redis** — по-прежнему самый быстрый и дешёвый по CPU, но всё хранится в RAM: ~325 Б на задачу, 430M задач — это ~140 GB.

**Итог для задачи из ADR (5k/s, глубина до суток, по одной задаче без буфера на продюсере):**
- По соотношению CPU / RAM / латентность лучше всех **Tarantool vinyl** (спейс на час + drop) и **Scylla**.
- Если продюсер может батчить — **PostgreSQL** с COPY и DROP партиций.
- Брокеры (RabbitMQ, RocketMQ) и MongoDB с удалением документов — хуже по ресурсам.

### Сколько железа нужно под ADR: 5k/s, глубина до 430M задач, одна нода без реплик

Оценка грубая. Цены условные, как в облаке: 1 vCPU = $20/мес, 1 GB RAM = $5/мес, 1 GB SSD = $0.1/мес.
- **CPU** — стационарное потребление из матрицы ×2 запаса, не меньше 1 ядра.
- **Хранилище** — байт на задачу × 430M.
- **RAM** — что движок реально занимал, для Redis и RabbitMQ — пропорционально данным.

**Вывод по соотношению производительность / ресурсы / стоимость:**
1. **Tarantool vinyl** — лучший баланс:
   - вторая после Redis одиночная запись на ядро (67k/s);
   - меньше всех RAM;
   - p99 2 ms на 5k/s;
   - дешёвое дисковое хранение.

   Слабое место — чтение, 0.3M/s. Для нагрузки ADR (~9k/s) это запас ×35.
2. **Scylla** — близко к Tarantool по CPU и латентности, но на пределе проседает при 1 GB на 4 шарда. Ей нужна память по рекомендации, ~2 GB на ядро.
3. **PostgreSQL** — самый дешёвый по CPU в стационаре и лучший на пачках и на чтении. Но одиночная запись — 19k/s на ядро и p99 30+ ms, а хранение с WAL самое объёмное.
4. **Cassandra и MongoDB** работают, но в 2–3 раза дороже по CPU на ту же нагрузку. MongoDB — только в варианте «коллекция на час + drop».
5. **RocketMQ** удобен: отложенная доставка встроена. Но стоит в 2 раза дороже по CPU и в 3 раза по диску.
6. **Redis и RabbitMQ** — самые дорогие при глубине очереди в сутки: всё или почти всё хранится в RAM.

## Пики на больших задачах: payload 5–10 KB (в среднем 7.5 KB), 1 минута

**Отличия от прогона на 300 Б:**
- **Лимит объёма.** Запись останавливается после 1M задач (~7.5 GB): на Docker VM свободно ~27 GB. Движки быстрее ~17k/s мерились меньше минуты.

- **Сжатие в клиенте RocketMQ выключено.** По умолчанию клиент жмёт zlib'ом тело больше 4 KB, остальные драйверы не жмут.

**Что изменилось по сравнению с 300 Б:**
- **Узкое место — байты, а не операции.** Выигрывают движки с append-only логом: Redis (AOF), RabbitMQ (message store), RocketMQ (commitlog). LSM-движки при маленькой памяти (memtable/L0 по 128–256 MB) упираются в дамп и компакцию:
  - Tarantool vinyl: регулятор ограничивает запись скоростью дампа ~100 MB/s, компакция за минуту переписала ~7 GB;

- **Tarantool падает со 123k/s до 10–12k/s.** Пачки у него не быстрее одиночной записи: транзакция на ~750 KB ждёт регулятора.
- **MongoDB лучший из БД на пачках (66k/s), Cassandra — на одиночной записи (28k/s).**
- **RabbitMQ пишет быстро, но читает всего 6.7k/s.** Это меньше 8.6k/s, нужных ADR днём.
- **Redis:** 430M × 7.5 KB = 3.2 TB RAM — вне рассмотрения.

### Что это значит для ADR при задачах 5–10 KB

- **Объём.** 5k/s × 7.5 KB = 38 MB/s записи и ~65 MB/s чтения днём. Очередь на сутки — 430M × 7.5 KB ≈ **3.2 TB** на каждую ноду, без сжатия. Объём хранения теперь главная статья расходов: с 1 мастером и 2 репликами это ~10 TB SSD плюс место под компакцию.
- **Запас по одиночной записи над 5k/s на ноде 4 CPU / 1.5 GB:**
  - Cassandra — ×5.5;
  - RocketMQ — ×6, но диск ×2: ~6.5 TB на ноду;
  - Tarantool — ×2.4;
  - MongoDB — ×2.5, на пачках ×13;
  - PostgreSQL — ×1.8, на пачках ×3;
  - Scylla — ×1.3, ей мало памяти.

  Запаса ×20+, как на 300 Б, нет ни у кого. На проде нужна память под memtable и page cache: 8–16 GB вместо 1.5 GB.
- **Сжатие.** Реальный payload (JSON, тексты) обычно сжимается в 3–5 раз. Scylla и Cassandra (LZ4 на SSTable), MongoDB (snappy/zstd) и PostgreSQL (TOAST pglz/lz4) это используют, у них и диск, и пропускная способность вырастут кратно. У Tarantool CE сжатия данных нет. В Enterprise есть сжатие полей кортежа (zstd/lz4); работает ли оно с vinyl, надо проверить. Иначе жать payload придётся в приложении. Стоит проверить на реальных payload'ах.
- **Payload вне планировщика.** Если payload можно держать отдельно (blob/KV по id) и класть в планировщик только ссылку (~300 Б), остаются цифры прогона на 300 Б. Тогда Tarantool снова лучший.

## Kafka без отдельного хранилища: кольцевые топики-слоты

Прогоны 2026-11-01: `kafka-20261101-*` (матрица), `peak-all-1101-1201-kafka-*`, `peak-big-1101-1204-kafka-*`, лог `run-kafka.log`.

**Схема.**
- Кольцо топиков `ring-NNN`, слот 1 ч или 5 мин. Кольцо = горизонт + 2 слота (26 или 290 топиков), поэтому запись никогда не попадает в слот, который сейчас читается.
- Продюсер пишет задачу в топик слота её времени исполнения.
- Когда слот закончился, консюмер вычитывает его целиком до high watermark, зафиксированного на старте. Затем `DeleteRecords` до того же offset: это аналог DROP партиции и одновременно сохранённый прогресс консюмера.

**Результаты.**
- **Самый дешёвый и быстрый вариант из всех, где данные на диске.**
  - Стационар 5k/s: p99 записи 3 ms, 0.4–0.6 ядра, 0.65 GB RAM, ~340 Б на задачу.
  - Потолок одиночной записи ~250–260k/s при ~1 ядре.
  - Пачки ~840k/s, вычитка 2–5M/s.
  - На задачах 5–10 KB — лучший результат в тесте: 60k/s одиночными (460 MB/s), вычитка 123k/s.
  - Причина: append-only лог без индексов и компакции, удаление — целыми сегментами.
- **Цена — точность доставки = длина слота.**
  - Внутри топика задачи лежат в порядке записи, а не исполнения. Поэтому слот целиком доступен только после своего конца.
  - Кольцо по 1 ч: опоздание до 60 мин, в среднем ~30. По 5 мин: до 5 мин.
  - Нагрузка в стационаре одинакова, разница только в точности и числе топиков: 26 × 4 = 104 партиции против 290 × 4 = 1160.
- **Чтение идёт всплесками.** Слот выдаётся разом:
  - 1 ч при 5k/s — до 18M задач в начале часа;
  - 5 мин — ~1.5M задач каждые 5 минут.

  Если нижестоящий Kafka-топик или сервис не любит пики, консюмеру нужен rate limit.
- **Точнее слота.** Можно читать 5-минутный слот заранее и раздавать задачи по минутам из памяти консюмера. Это ~1.5M задач: ~0.5 GB при 300 Б и ~11 GB при 7.5 KB. Либо брать слоты по 1 мин: ~1440 топиков, это много для одного кластера.

**Ограничения схемы (стенд их не проверяет).**
- Горизонт жёсткий. Задачу дальше горизонта нельзя записать: она попадёт в слот следующего круга. Задачу со временем в прошлом или в текущем слоте продюсер должен класть сразу в целевой топик.
- Отменить или изменить задачу нельзя: топик append-only. Отмена — только флагом при доставке.
- Репликация: RF=3 на 3 ДЦ с `acks=all`, `min.insync.replicas=2` добавит RTT между ДЦ к записи, как и у остальных движков. Зато failover штатный: лидер партиции переезжает сам, прогресс консюмера (log start offset) реплицируется вместе с данными.

## Что было не так по ходу и исправлено

- Kafka: клиенту была выставлена пачка 4 MB, брокер по умолчанию принимает ~1 MB (`MESSAGE_TOO_LARGE`) — на 5–10 KB падали prefill и часть пачек. Опция убрана, пиковые batch/read на больших задачах перегнаны, старое лежит в `invalid-kafka-maxbytes/`.
- PG `delete`: внешний `DELETE` не фильтровал по `minute`/`shard`, шёл Seq Scan по всей партиции. Исправлено и перепрогнано, старое лежит в `invalid-pg-delete/`.
- Scylla не стартовала с лимитом 1.5 GB — добавлен `--reserve-memory 300M`.
- RabbitMQ с 1.5 GB — memory alarm, прогон остановлен (`aborted-rabbit-1536m/`), перегнан с 4 GB.
- RocketMQ: `SendAsync` в rocketmq-client-go v2.1.2 падает с nil pointer при таймауте под нагрузкой. Пачки теперь отправляются через параллельный `SendSync`, пиковый батч-прогон перегнан.
- RocketMQ maxw: бенч 3 минуты ждал PREFILL_ETA при пустом prefill. CPU выше посчитан только по активной части. В скриптах теперь `PREFILL_ETA=0s` для прогонов без prefill.

## Чего этот стенд не показывает

- Реплики: RF=1, у PG нет синхронной реплики, у брокеров нет зеркал/кворума, у Tarantool нет репликации.
- Durability: у PG коммит с fsync; у RabbitMQ confirm после записи на диск; у Scylla, Cassandra, Tarantool, MongoDB (w:1 без j) и RocketMQ (ASYNC_FLUSH) — асинхронный сброс на диск.
- Глубину 430M задач (здесь 10M).
- Шум: на той же Docker VM работали посторонние контейнеры.
